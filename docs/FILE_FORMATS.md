# File Formats

This page shows tiny examples of the files GROND reads and writes. The numbers
below are illustrative, not a reference dataset. They are meant to help a new
user recognize the shape of each file before opening a real run directory.

## Input Directory

GROND usually starts from two places: a row-preserving integration directory and
a solved structure directory. For XDS, the integration directory should come
from the row-preserving integration pass, typically with
`PROFILE_FITTING=FALSE` and `MINPK=90.0`. For DIALS, the equivalent input is the
matching `integrated.refl` and `integrated.expt` pair from `dials.integrate`.

```text
my_xds_directory/
  INTEGRATE.HKL
  XPARM.XDS              # or GXPARM.XDS
  XDS.INP
  INTEGRATE.LP

my_structure_directory/
  structure.res          # or structure.cif
  structure.hkl          # baseline solved-model reflection file, when used
```

```text
my_dials_directory/
  integrated.refl        # signed row table with intensity.sum.value
  integrated.expt        # beam, scan, detector, crystal, scan-varying A
  dials.integrate.log
```

`INTEGRATE.HKL` is the most important input because each numeric row is one
measured spot observation. The exact XDS header is longer than this sketch, but
the useful part looks like a table of signed indices, intensity, uncertainty,
and geometry-like columns.

```text
!FORMAT=XDS_ASCII
!NX=4148 NY=4362 QX=0.0750 QY=0.0750
!ORGX=2074.2 ORGY=2181.6 DETECTOR_DISTANCE=720.0
!H K L     IOBS      SIGMA   XCAL    YCAL    ZCAL    RLP    PEAK  CORR
   1  0  2   1284.50    42.10  1912.4  2105.7   18.0  0.021   142  91.4
   0  1  3    422.80    27.60  2063.9  1988.2   18.0  0.034    61  88.7
  -2  1  1     96.30    19.20  2251.5  2320.4   19.0  0.058    18  74.9
```

`XPARM.XDS` or `GXPARM.XDS` provides the geometry contract: detector axes,
beam direction, rotation axis, unit cell, and orientation. GROND uses it to put
spot positions, reciprocal-space vectors, excitation errors, and frame numbers
into one coordinate system.

For DIALS, `GROND import-dials` or `GROND auto --dials-refl ... --dials-expt ...`
writes a prepared compatibility directory:

```text
dials_grond_bridge/
  INTEGRATE.HKL                  # XDS-like row contract generated by GROND
  DIALS_A_AT_SCAN_POINTS.txt     # one 3x3 A matrix per DIALS scan point
  dials_bridge_summary.json      # row counts, flags, Sg validation
  DIALS_BRIDGE_README.md
```

The generated `INTEGRATE.HKL` uses `intensity.sum.value * lp / partiality` by
default, stores `100 * partiality` in the `PEAK` column, stores `lp` in `RLP`,
and keeps the exact signed DIALS `miller_index`. GROND's default `--min-peak 90`
therefore means DIALS partiality `>= 0.90`. The DIALS bridge also writes
`!DIALS_SIGMA_MODE` and `!DIALS_SIGMA_MULTIPLIER` header records. In the default
auto mode, GROND fits an empirical duplicate-scatter variance model when
enough symmetry-equivalent rows exist and only falls back to detector-gain checks when duplicate support is insufficient. The
intensities are not changed by sigma scaling.

For integrations from other software, use the portable row contract documented
in [PORTABLE_INPUTS_AND_ENDPOINTS.md](PORTABLE_INPUTS_AND_ENDPOINTS.md). The row
table can be CSV, TSV, or JSON Lines. The smallest useful CSV table looks like
this:

```csv
row_id,dataset_id,h,k,l,Iobs,sigma_Iobs,frame,x_px,y_px,partiality,lp,profile_correlation,bbox_z0,bbox_z1
0,crystal_a,1,0,2,1284.5,42.1,18.0,1912.4,2105.7,1.00,1.0,91.4,17.5,18.5
1,crystal_a,0,1,3,422.8,27.6,18.0,2063.9,1988.2,0.95,1.0,88.7,17.4,18.6
```

The matching metadata sidecar supplies the geometry that a merged HKL cannot
carry:

```json
{
  "schema_version": "grond-row-v1",
  "dataset_id": "crystal_a",
  "geometry": {
    "wavelength_A": 0.02508,
    "incident_beam_direction": [0.0, 0.0, 1.0],
    "rotation_axis": [1.0, 0.0, 0.0],
    "starting_frame": 1.0,
    "starting_angle_deg": 0.0,
    "oscillation_range_deg": 0.5,
    "unit_cell": [7.0, 8.0, 9.0, 90.0, 90.0, 90.0],
    "reciprocal_A_matrix": [
      [0.1428571429, 0.0, 0.0],
      [0.0, 0.125, 0.0],
      [0.0, 0.0, 0.1111111111]
    ]
  }
}
```

`GROND row-validate --rows rows.csv --metadata metadata.json --write-xds-dir
portable_bridge` validates the files and writes a `GROND_PORTABLE_XDS_COMPAT`
directory that the current engine can process. This bridge is only a compatibility
layer; it keeps the original source and row-contract manifest in the output.

The structure file supplies the atomic model. GROND accepts `RES` or `CIF`.
For a CIF, the atom loop has the usual atom labels, element types, fractional
coordinates, and displacement values.

```text
loop_
_atom_site_label
_atom_site_type_symbol
_atom_site_fract_x
_atom_site_fract_y
_atom_site_fract_z
_atom_site_U_iso_or_equiv
C1  C  0.1254  0.3367  0.4821  0.032
O1  O  0.2186  0.2941  0.5114  0.041
N1  N  0.0813  0.4472  0.3910  0.035
```

## Prep JSON

For one dataset, the command line can point directly at files. For multiple
datasets, `GROND prep` writes a small manifest. Each dataset keeps its own XDS
directory, name, and optional metadata, while sharing the structure and baseline
HKL.

```json
{
  "structure": "/data/project/model/structure.res",
  "baseline_hkl": "/data/project/model/structure.hkl",
  "datasets": [
    {
      "name": "crystal_a",
      "xds_dir": "/data/project/crystal_a/xds",
      "integrate_hkl": "/data/project/crystal_a/xds/INTEGRATE.HKL",
      "xparm": "/data/project/crystal_a/xds/XPARM.XDS"
    },
    {
      "name": "crystal_b",
      "xds_dir": "/data/project/crystal_b/xds"
    }
  ]
}
```

## Reflection JSONL

GROND turns the XDS rows into an observation ledger. The ledger is JSON Lines:
one JSON object per line. A row is one measured spot, not a merged unique
reflection. Keeping row identity is what lets GROND audit weak rows, frame
trends, geometry, hand, and thickness without hiding everything inside a merge.

```jsonl
{"dataset":"crystal_a","row_index":0,"hkl":[1,0,2],"iobs":1284.5,"sigma":42.1,"frame":18.0,"detector_px":[1912.4,2105.7],"rlp":0.021,"peak":142.0,"corr":91.4,"source":{"file":"INTEGRATE.HKL","line":1042},"geometry":{"xparm":"XPARM.XDS"}}
{"dataset":"crystal_a","row_index":1,"hkl":[0,1,3],"iobs":422.8,"sigma":27.6,"frame":18.0,"detector_px":[2063.9,1988.2],"rlp":0.034,"peak":61.0,"corr":88.7,"source":{"file":"INTEGRATE.HKL","line":1043},"geometry":{"xparm":"XPARM.XDS"}}
{"dataset":"crystal_a","row_index":2,"hkl":[-2,1,1],"iobs":96.3,"sigma":19.2,"frame":19.0,"detector_px":[2251.5,2320.4],"rlp":0.058,"peak":18.0,"corr":74.9,"source":{"file":"INTEGRATE.HKL","line":1044},"geometry":{"xparm":"XPARM.XDS"}}
```

Field names can grow as GROND learns more about a row. A run may add
resolution, reciprocal-vector components, transform labels, split labels,
profile-box measurements, or raw-image metadata when those inputs exist.

## Native Row Table

The main numerical output is a CSV table. It carries the original observation,
the current dynamical prediction, the Born or kinematic reference prediction,
and the terms needed to understand residuals.

```csv
row_index,h,k,l,d_A,target_I,sigma_eff,row_resolution_factor,dyn_raw_unmodulated,dyn_raw,born_raw,dyn_scaled,born_scaled,split
0,1,0,2,0.842,1284.50,42.10,1.118,1091.10,1219.80,1038.40,1257.62,1070.58,work
1,0,1,3,0.914,422.80,27.60,1.061,415.83,441.20,389.50,454.22,401.25,work
2,-2,1,1,1.284,96.30,19.20,0.912,130.15,118.70,101.60,122.29,104.65,free
```

This table is the right place to inspect all-row R factors, weak-row bias,
resolution trends, detector-radius trends, dose/frame trends, and whether a
proposed nuisance term is helping or merely fitting noise.

## Corrected HKL

When an endpoint is promoted, GROND writes corrected reflection files for
downstream crystallographic programs. The exact header and scale convention can
depend on the target program, but the body is still a compact reflection table:
indices plus corrected intensity or amplitude and uncertainty.

```text
   1   0   2    1245.30     43.20
   0   1   3     430.10     28.00
  -2   1   1     110.60     20.10
```

GROND records how the corrected file was produced, including the selected hand,
thickness band, transform, geometry policy, basis size, and accepted nuisance
terms.

The endpoint `manifest.json` also records any post-Bloch uncertainty policy.
For the default final endpoint this is usually a `post_bloch_sigma` block with
`policy=uniform_z_rms`, one fitted `sigma_scale`, and train, held-out, and
all-reflection RMS(z) diagnostics. The corrected intensities in the HKL are not
changed by this block; only the endpoint sigmas are scaled.

## Summary JSON

Each major stage writes a machine-readable summary. The keys are stable enough
for scripts, while the values remain explicit about what population was scored.

```json
{
  "dataset": "crystal_a",
  "stage": "adaptive_final",
  "selected": {
    "transform": "identity",
    "hand": "original",
    "thickness_nm": 0.86,
    "basis_n": 60,
    "quadrature_q": 9
  },
  "raw_rows": {
    "n": 184320,
    "R1_all": 0.1123,
    "wR2_all": 0.2970,
    "R1_strong": 0.0512
  },
  "merged_endpoint": {
    "n_unique": 4820,
    "R1_obs": 0.0914,
    "R1_all": 0.1268
  }
}
```

## Command Log and Resume State

`logs/commands.jsonl` is a chronological ledger. It lets a user see what GROND
launched, how long it took, and whether the stage succeeded.

```jsonl
{"event":"start","stage":"crystal_a_preflight","time":"2026-05-18T14:03:02","cmd":["GROND","auto","--xds-dir","..."]}
{"event":"finish","stage":"crystal_a_preflight","elapsed_s":2.41,"returncode":0}
{"event":"finish","stage":"crystal_a_adaptive_final","elapsed_s":612.80,"returncode":0}
```

`grond_progress.json` is the resume file. If the process is interrupted, GROND
uses this file to skip stages that already finished successfully.

```json
{
  "completed": {
    "crystal_a_preflight": {"elapsed_s": 2.41, "status": "ok"},
    "crystal_a_scout_hand_alt": {"elapsed_s": 81.32, "status": "ok"}
  },
  "running": null,
  "interrupted_stage": null
}
```

## Maps and Reports

Map files are written when the necessary external map tools are available.
Human-readable `REPORT.md` files sit next to the machine-readable summaries and
explain which branch won, which branches were rejected, and what residual
patterns still deserve attention.
