# Performance

GROND uses process-level row parallelism and pins BLAS helper threads to avoid oversubscription. By default, `--workers 0` uses a conservative fraction of the visible CPU cores. Set `--workers` explicitly only after checking memory and filesystem behavior.

Generated Bloch caches are runtime artifacts, not package data. `GROND auto` keeps its prediction caches under the run output directory unless `--prediction-cache-dir` is supplied. Legacy standalone engines and cache misses that need a reusable U_g cube write under `GROND_CACHE_DIR` when that environment variable is set, otherwise under the operating-system user cache directory such as `~/Library/Caches/grond` on macOS or `$XDG_CACHE_HOME/grond` on Linux. On shared servers, set `GROND_CACHE_DIR` to a fast scratch filesystem if the home directory is slow or quota-limited. Installed GROND package directories should remain read-only.

The fastest reliable improvement is usually fewer final predictions, not more hardware. The automatic workflow therefore narrows transforms, polarity, thickness, nuisance terms, and basis size before launching final row predictions. The transform gate first tries a metadata prefilter when `--baseline-hkl` is available: GROND compares signed HKL/intensity overlap between the raw XDS rows and the solved/XSCALE/SHELX HKL, promotes a single transform only when the correlation and gap are strong, and otherwise keeps the top ambiguous candidates or falls back to the full list. The remaining transform gate is two-stage: `--scout-n-basis 8 --scout-n-points 3` touches the surviving candidates cheaply, then `--transform-rerank-top 3` reruns only the best candidates with `--transform-rerank-n-basis 24 --transform-rerank-n-points 10`. Transform scouts are queued across candidates and datasets with `--transform-scout-jobs`; the default derives a core-safe outer queue from `--workers` and keeps each scout subprocess at `--transform-scout-workers-per-job 1` to avoid launching many scouts that each try to consume the whole server. Full auto keeps the production quadrature at Q20, but it does not guess a fixed N; it scans rowwise Sg support and uses the observed maximum plus a 10-beam margin, limited to 500. The support pool follows the selected resolution limit rather than a fixed 0.8 A top-up, because high-resolution endpoint rows need high-resolution coupled beams to be treated at the same theory level.

For example, on a 100-core node, `--workers 85 --transform-scout-jobs 0 --transform-scout-workers-per-job 1` lets the transform gate run up to 85 scout subprocesses across all datasets and candidates. If each scout needs more row-level workers, set both knobs explicitly, such as `--transform-scout-jobs 20 --transform-scout-workers-per-job 4`, so the product stays near the intended core budget.

When the signed HKL transform is known, `--trust-hkl-transform` is faster than narrowing the candidate list because it skips the transform stage entirely. Use it together with an explicit `--hkl-transform`. This is meant for reproducible reruns and well-tracked XDS/DIALS pipelines, not for ambiguous or newly imported data.

Use `--full-fast` when you want the automatic path, not just triage, but need a same-session answer. This profile keeps the decision tree on and runs lightweight structure update, while pinning N=24/Q=10, using one endpoint polish pass, turning endpoint feedback off, turning observation-polish endpoint promotion off, and using quick forensics. Its structure-update budget is atom-count aware: small models keep a fuller ADP probe, while larger models automatically use fewer objective rows and fewer function evaluations unless those limits are supplied explicitly. It is intended to produce a scientifically useful intermediate model and a timing estimate for whether the full Q20 polish is worth launching.

Structure-update blocks have a plateau gate in the high-level CLI. By default, `GROND auto` passes `--structure-early-stop-window 64 --structure-early-stop-min-improvement 2e-5 --structure-early-stop-metric data_rms` into the finite-difference engines. A block can still run long when every accepted probe keeps improving the row objective, but it should not spend days repeating xyz or ADP calls after the data residual has stopped moving. Increase the window or set it to 0 only for deliberate diagnostics.

For a still cheaper stress scout, add `--full-fast-n-basis 10 --full-fast-n-points 5`. This keeps the same decision tree but should be treated as a diagnostic shortcut. In local bounded tests it saved modest wall time, while the N24/Q10 profile is now the default compromise for endpoint and all-row statistics.

The post-final scale-polish pass is another speed and rigor guard. It does not recompute Bloch waves. Instead, it asks whether the dense frame-scale curve can be represented by fewer smooth neighboring-frame segments while keeping the exact detector scale grid and preserving all-row residuals within the declared gates. The output now includes AIC/BIC-style information criteria computed from the native row-space weighted residual and total nuisance/scale parameter count, but those criteria are used only after the residual gates have passed. This prevents a very coarse scale model from winning only because it has fewer parameters while quietly damaging the row model. The final publication table repeats the full-to-compact parameter counts, all-row residual penalties, and information-criterion diagnostics, so the promoted compact model cannot quietly trade a large R-factor penalty for a smaller parameter count.

The multi-dataset inclusion policy is also cheap. It reads completed row tables, compares per-crystal quality to the best crystal set, estimates unique reflection gain, and writes sigma-weighted row-table copies. No Bloch predictions are recalculated by this gate. The expensive shared-model model update only sees crystals marked `primary` or `downweight`, while the endpoint merge can still consume `completeness_only` rows with a low uncertainty weight. Before the corrected-HKL endpoint is merged, GROND fits one scalar per dataset from overlapping corrected reflections. This is an XSCALE-like normalization after the dynamical correction; it prevents per-crystal raw integration scale offsets from being mistaken for structural disagreement. The default combined endpoint also calibrates each dataset's corrected endpoint sigmas independently, then inflates merged-reflection sigmas when the contributing datasets disagree beyond their formal errors. These are scalar or merge-level bookkeeping passes, not new Bloch simulations, so they add little wall time compared with row prediction.

Full `GROND auto` is intentionally more expensive than `--fast`: it screens detector-position scale fields, endpoint lambda values, and five SHELXL endpoint polish cycles with active `WGHT` promotion. Final endpoints and SHELXL feedback cycles also apply the one-scalar post-Bloch `uniform_z_rms` sigma calibration by default, which is cheap compared with Bloch prediction and keeps weighted endpoint statistics on a declared residual scale. Nonzero endpoint-B values are not part of the production default; use `--endpoint-b-grid` only for a diagnostic stress test, because this correction can lower R factors by reshaping the endpoint data while making the updated model and maps worse. The default full path spends time on row-level physics first and keeps the final corrected-HKL endpoint at B=0.

The publication endpoint chooser is cheap because it only reads endpoint summaries. It does not rerun Bloch waves or endpoint regularization; it prevents a low-residual diagnostic correction from becoming the final reported endpoint without passing the physical gate.

The resolution-limit audit is intentionally cheap. It reads the final `native_dyn_calc.csv` row tables and recomputes shell, cumulative, held-out, and GROND row/MR merged residual statistics without recalculating Bloch waves. Keeping this as a row-table gate lets `auto` make per-dataset and combined endpoint resolution decisions in seconds to minutes, while the expensive time remains concentrated in the final dynamic prediction and structure-update steps.

The late Sg-window scout is deliberately small. It reruns the final pinned nuisance model over a short list of fixed global rocking-window widths, usually `0.003,0.004,0.006,0.008 A^-1`, at N24/Q10 unless changed. Promotion requires an all-row wR2 gain and no meaningful held-out wR2 penalty. GROND does not choose a separate Sg width per reflection from the observed intensity; that would look good numerically but would be fitting the residual unless the width came from independent raw-image profile metadata.

The installable package ships an experimental JAX CUDA eigensolver backend, but the production default remains SciPy CPU parallelism. On an internal Linux CUDA server, the CUDA path correctly used three RTX 2080 Ti GPUs and matched SciPy on a benchmark dataset, but the optimized SciPy path with 10 CPU workers was still much faster for the current N128/Q20 workload. Future accelerators should be accepted only when they reproduce row-level dynamic intensity, Born intensity, basis size, endpoint statistics, and map-producing reflection files against the SciPy reference and beat the CPU-parallel reference wall time.

`--compute-backend jax_cpu`, `jax_cuda`, `jax`, `jax_auto`, and `jax_mps` are experimental eigensolver backends for the same Bloch kernel. The padded variants, for example `jax_cpu_padded` and `jax_cuda_padded`, follow Takanori Nakane's fixed-size matrix suggestion by padding matrix dimensions into small buckets so JAX compiles fewer shapes. In local production-like N108/Q20 timing probes, bucketed JAX CPU matched SciPy numerically and improved hot-loop JAX timing relative to exact-size JAX groups, but it still remains opt-in until it wins whole `GROND auto` runs on real data. `jax_cuda` batches same-size matrices and uses JAX `pmap` across visible CUDA devices, while the other JAX options are mostly diagnostic. A backend is acceptable only if complex Hermitian `eigh`, non-Hermitian `eig`, raw `Idyn`, endpoint statistics, and maps match SciPy within numerical tolerance. On Apple Silicon, JAX/MPS may expose the GPU but still fail complex eigensolvers; in that case GROND raises a backend error instead of silently falling back.

`jax_mps_real_expm` and `jax_mps_real_expm_padded` are a guarded Apple-Metal experiment. They avoid complex eigensolvers by embedding the complex Bloch propagation into a real matrix and using fixed-order scaling/squaring matrix exponentials. This made MPS runnable on the local laptop, but it did not beat CPU on 370 and it is limited to float32 on current JAX/MLX. On a 370 N24/Q10, 64-row benchmark, dense SciPy took 2.02 s, `scipy_bethe` took 1.19 s, and `jax_mps_real_expm` took 2.07 s with matching displayed residuals. On a 370 N108/Q20, 8-row check, `jax_mps_real_expm` was again slower and differed from SciPy by about `2e-4` maximum relative `dyn_raw`. Keep it opt-in unless a future Apple/JAX stack improves precision and whole-run speed.

The most useful speed backend today is `--compute-backend scipy_bethe`. It applies a physics-aware strong/weak-beam Schur reduction before diagonalization instead of sending a larger dense matrix to different hardware. On the 370 N108/Q20, 64-row benchmark, dense SciPy took 20.37 s. `scipy_bethe --bethe-variant schur_target --bethe-strong-count 64` took 9.03 s with maximum relative `dyn_raw` difference `8.8e-5`; count 80 recovered the dense SciPy row intensities exactly for that subset and took 9.36 s. A broader 128-row check was more conservative: dense SciPy took 20.09 s, Bethe-64 took 17.59 s with maximum relative `dyn_raw` difference `2.4e-4`, and Bethe-80 again recovered dense SciPy to displayed precision in 17.65 s. The speedup therefore depends on the basis-size and promotion mix, but the Schur-target variants are the right safe path to keep testing. The plain `truncate` variant took only 6.30 s on the 64-row check, but it changed `Idyn` by up to 21.5% and shifted the residuals, so it is a diagnostic stress test rather than a promoted backend.

The preserved JAX/Metal backup notes are in `docs/EXPERIMENTAL_JAX_BACKEND.md`.

## Experimental Row-Plan Cache

`--row-plan-cache readwrite` enables the first immutable row-plan cache for the SciPy Bloch path. It precomputes the row identity, signed support basis, target beam position, rocking-profile Sg values, profile quadrature weights, and flattened `h_j-h_i` difference-HKL lookup indices. Later predictions keep that row plan fixed and recompute only the current-model Fourier-potential values needed by the cached differences. The intent is LS1 feedback: the geometry and support contract stay frozen while the structure changes from cycle to cycle.

This cache is exact for a fixed frozen basis. On the 370 benchmark used during development, cached and uncached row predictions matched with zero displayed difference in `Idyn`, `Iborn`, and basis size. The row-plan summary records whether the cache was hit, rebuilt, or off, plus the number of unique difference HKLs used by the cached matrices.

Cache hits are validated before use. GROND checks the saved cache schema, source row hash, transform, requested row order, N/Q settings, quadrature policy, and required array layout. A stale, renamed, or incomplete cache is ignored and rebuilt instead of being trusted. The cached path also reports multiprocessing fallback reasons in the row-plan status block, so a slow run is easier to distinguish from a physics or backend change.

The current verdict is cautious. It is implemented and useful for testing, but it is not promoted as the default production speed path yet. On a 370 N30/Q10 100-row smoke test, the cache-hit prediction time improved from 0.260 s to 0.151 s after the cache existed, while rebuilding the cache was slower. On a 500-row N128/Q20 single-worker check, the cache hit improved prediction time from 22.86 s to 21.35 s. On the full 5094-row 370 N128/Q20 14-worker check, one run improved from 33.23 s to 29.64 s when row-table writing was enabled, but a no-CSV repeat went from 30.81 s uncached to 32.62 s cached. That is not a clear enough win to turn on automatically.

The likely bottleneck is no longer just row geometry setup. The cached path still constructs matrices in Python, still diagonalizes the same matrices, and on macOS still ships a large cache object through multiprocessing workers. The next real speed step is to avoid pickling the row-plan cache into every worker, memory-map or share the immutable arrays, skip full reciprocal-cube setup when a valid row-plan cache is present, and evaluate cached rows in larger same-size matrix buckets. Until those are done, `--row-plan-cache readwrite` should be treated as an opt-in benchmark and LS1 validation tool rather than a default.
