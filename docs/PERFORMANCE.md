# Performance

GROND uses process-level row parallelism and pins BLAS helper threads to avoid oversubscription. By default, `--workers 0` uses a conservative fraction of the visible CPU cores. Set `--workers` explicitly only after checking memory and filesystem behavior.

The fastest reliable improvement is usually fewer final predictions, not more hardware. The automatic workflow therefore narrows transforms, polarity, thickness, nuisance terms, and basis size before launching final row predictions. The transform gate first tries a metadata prefilter when `--baseline-hkl` is available: GROND compares signed HKL/intensity overlap between the raw XDS rows and the solved/XSCALE/SHELX HKL, promotes a single transform only when the correlation and gap are strong, and otherwise keeps the top ambiguous candidates or falls back to the full list. The remaining transform gate is two-stage: `--scout-n-basis 8 --scout-n-points 3` touches the surviving candidates cheaply, then `--transform-rerank-top 3` reruns only the best candidates with `--transform-rerank-n-basis 24 --transform-rerank-n-points 10`. Transform scouts are queued across candidates and datasets with `--transform-scout-jobs`; the default derives a core-safe outer queue from `--workers` and keeps each scout subprocess at `--transform-scout-workers-per-job 1` to avoid launching many scouts that each try to consume the whole server. Full auto keeps the production quadrature at Q20, but it does not guess a fixed N; it scans rowwise Sg support and uses the observed maximum plus a 10-beam margin, limited to 500. The support pool follows the selected resolution limit rather than a fixed 0.8 A top-up, because high-resolution endpoint rows need high-resolution coupled beams to be treated at the same theory level.

For example, on a 100-core node, `--workers 85 --transform-scout-jobs 0 --transform-scout-workers-per-job 1` lets the transform gate run up to 85 scout subprocesses across all datasets and candidates. If each scout needs more row-level workers, set both knobs explicitly, such as `--transform-scout-jobs 20 --transform-scout-workers-per-job 4`, so the product stays near the intended core budget.

Use `--full-fast` when you want the automatic path, not just triage, but need a same-session answer. This profile keeps the decision tree on and runs lightweight structure update, while pinning N=24/Q=10, using one endpoint polish pass, turning endpoint feedback off, turning observation-polish endpoint promotion off, and using quick forensics. Its structure-update budget is atom-count aware: small models keep a fuller ADP probe, while larger models automatically use fewer objective rows and fewer function evaluations unless those limits are supplied explicitly. It is intended to produce a scientifically useful intermediate model and a timing estimate for whether the full Q20 polish is worth launching.

Structure-update blocks have a plateau gate in the high-level CLI. By default, `GROND auto` passes `--structure-early-stop-window 64 --structure-early-stop-min-improvement 2e-5 --structure-early-stop-metric data_rms` into the finite-difference engines. A block can still run long when every accepted probe keeps improving the row objective, but it should not spend days repeating xyz or ADP calls after the data residual has stopped moving. Increase the window or set it to 0 only for deliberate diagnostics.

For a still cheaper stress scout, add `--full-fast-n-basis 10 --full-fast-n-points 5`. This keeps the same decision tree but should be treated as a diagnostic shortcut. In local bounded tests it saved modest wall time, while the N24/Q10 profile is now the default compromise for endpoint and all-row statistics.

The post-final scale-polish pass is another speed and rigor guard. It does not recompute Bloch waves. Instead, it asks whether the dense frame-scale curve can be represented by fewer smooth neighboring-frame segments while keeping the exact detector scale grid and preserving all-row residuals within tolerance. This reduces nuisance-parameter pressure without hiding the result, because the full candidate table and selected compact row table are written beside the final run. The final publication table repeats the full-to-compact parameter counts and the residual penalty in percentage points, so the promoted compact model cannot quietly trade a large R-factor penalty for a smaller parameter count.

The multi-dataset inclusion policy is also cheap. It reads completed row tables, compares per-crystal quality to the best crystal set, estimates unique reflection gain, and writes sigma-weighted row-table copies. No Bloch predictions are recalculated by this gate. The expensive shared-model model update only sees crystals marked `primary` or `downweight`, while the endpoint merge can still consume `completeness_only` rows with a low uncertainty weight. Before the corrected-HKL endpoint is merged, GROND fits one scalar per dataset from overlapping corrected reflections. This is an XSCALE-like normalization after the dynamical correction; it prevents per-crystal raw integration scale offsets from being mistaken for structural disagreement.

Full `GROND auto` is intentionally more expensive than `--fast`: it screens detector-position scale fields, endpoint lambda values, and five SHELXL endpoint polish cycles with active `WGHT` promotion. Nonzero endpoint-B values are not part of the production default; use `--endpoint-b-grid` only for a diagnostic stress test, because this correction can lower R factors by reshaping the endpoint data while making the updated model and maps worse. The default full path spends time on row-level physics first and keeps the final corrected-HKL endpoint at B=0.

The publication endpoint chooser is cheap because it only reads endpoint summaries. It does not rerun Bloch waves or endpoint regularization; it prevents a low-residual diagnostic correction from becoming the final manuscript endpoint without passing the physical gate.

The resolution-limit audit is intentionally cheap. It reads the final `native_dyn_calc.csv` row tables and recomputes shell, cumulative, held-out, and GROND row/MR merged residual statistics without recalculating Bloch waves. Keeping this as a row-table gate lets `auto` make per-dataset and combined endpoint resolution decisions in seconds to minutes, while the expensive time remains concentrated in the final dynamic prediction and structure-update steps.

The late Sg-window scout is deliberately small. It reruns the final pinned nuisance model over a short list of fixed global rocking-window widths, usually `0.003,0.004,0.006,0.008 A^-1`, at N24/Q10 unless changed. Promotion requires an all-row wR2 gain and no meaningful held-out wR2 penalty. GROND does not choose a separate Sg width per reflection from the observed intensity; that would look good numerically but would be fitting the residual unless the width came from independent raw-image profile metadata.

The installable package ships an experimental JAX CUDA eigensolver backend, but the production default remains SciPy CPU parallelism. On an internal Linux CUDA server, the CUDA path correctly used three RTX 2080 Ti GPUs and matched SciPy on a benchmark dataset, but the optimized SciPy path with 10 CPU workers was still much faster for the current N128/Q20 workload. Future accelerators should be accepted only when they reproduce row-level dynamic intensity, Born intensity, basis size, endpoint statistics, and map-producing reflection files against the SciPy reference and beat the CPU-parallel reference wall time.

`--compute-backend jax_cpu`, `jax_cuda`, `jax`, `jax_auto`, and `jax_mps` are experimental eigensolver backends for the same Bloch kernel. The padded variants, for example `jax_cpu_padded` and `jax_cuda_padded`, follow Takanori Nakane's fixed-size matrix suggestion by padding matrix dimensions into small buckets so JAX compiles fewer shapes. In local production-like N108/Q20 timing probes, bucketed JAX CPU matched SciPy numerically and improved hot-loop JAX timing relative to exact-size JAX groups, but it still remains opt-in until it wins whole `GROND auto` runs on real data. `jax_cuda` batches same-size matrices and uses JAX `pmap` across visible CUDA devices, while the other JAX options are mostly diagnostic. A backend is acceptable only if complex Hermitian `eigh`, non-Hermitian `eig`, raw `Idyn`, endpoint statistics, and maps match SciPy within numerical tolerance. On Apple Silicon, JAX/MPS may expose the GPU but still fail complex eigensolvers; in that case GROND raises a backend error instead of silently falling back.
